# BankLite – Smart Loan Origination System

BankLite is a role-based full-stack loan workflow demo built with React on the frontend and Flask on the backend. It supports customer login, loan application submission, rule-based credit scoring, officer review, mandatory underwriting comments, and AI-assisted review for pending applications.

The project now includes a machine learning extension that returns a Random Forest prediction and SHAP-based feature contributions alongside the existing rule-based score. The original application workflow remains unchanged: applications are submitted as pending, and the credit officer makes the final decision.

## What the app does today

The current workflow follows these steps:

1. A user logs in through the React frontend.
2. The backend validates credentials and returns a session token.
3. A customer submits a loan application with applicant, financial, and property details.
4. The backend calculates the existing rule-based credit score.
5. The ML service generates a Random Forest prediction and the three largest absolute SHAP feature contributions.
6. The application is stored as pending, and the submission response includes the scoring outputs.
7. A credit officer reviews pending applications from the officer dashboard.
8. The officer can approve or reject an application after entering comments.
9. The officer can also generate an AI-assisted review for the selected application.

The ML recommendation does not automatically approve or reject an application.

## Current features

### Customer flow

- Login with role-based routing to the customer dashboard.
- View personal loan applications and their status.
- Submit a new loan application through the application form.
- Track application progress as pending, approved, or rejected.

### Officer flow

- Access a protected officer dashboard.
- View pending applications in a queue.
- See a credit score distribution chart for pending loans.
- Open an underwriting console for a selected application.
- Approve or reject applications only after entering comments.
- Generate an AI-assisted review for a loan application.

### Backend capabilities

- Flask REST API with protected routes.
- Token-based authentication using session tokens stored in the database.
- Existing rule-based credit scoring for loan applications.
- Random Forest prediction returned with the loan submission response.
- SHAP-based local feature contributions returned with the prediction.
- Audit log insertion for officer decisions.
- AI-assisted review generation for pending loan applications.

### Machine learning extension

- Separate training script comparing:
  - Logistic Regression
  - Random Forest
  - XGBoost
- Model comparison using accuracy, ROC-AUC, precision, recall, and F1 score.
- Random Forest selected for deployment based on class-0 recall in the recorded experiment.
- Saved model and feature-column artefacts for inference.
- Global SHAP beeswarm and importance plots.
- A local SHAP waterfall plot.
- API output containing the model recommendation and the top three feature contributions.

The existing AI-assisted review feature and the SHAP explanation service are separate components. SHAP contributions are computed from the trained model rather than generated by a language model.

## Setup instructions

### 1. Prerequisites

- Python 3.10 or later, with package versions compatible with the saved model.
- Node.js and npm.
- PostgreSQL running locally.
- Git.

### 2. Clone the repository

```powershell
git clone [https://github.com/bassequus/Banklite.git](https://github.com/bassequus/Banklite.git)
cd Banklite
```

If you already have the project locally, open your existing project folder instead.

### 3. Backend setup

From the project root:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

If the ML dependencies have not yet been added to `requirements.txt`, install them in the activated environment:

```powershell
python -m pip install scikit-learn xgboost shap pandas numpy matplotlib joblib
```

For reproducibility, use the package versions from the environment that produced the saved model. Loading an existing model with different library versions may cause compatibility problems.

### 4. Database and service configuration

Make sure the PostgreSQL settings used by [backend/config.py](backend/config.py) match your local environment.

Use [database/schema.sql](database/schema.sql) to set up the required database tables, after reviewing it for your installation.

The existing AI-assisted review functionality may also require external-service configuration. Check the implementation under `backend/utils/`.

Do not commit real database passwords, API keys, or session tokens. Keep secrets in local environment variables or another untracked configuration mechanism supported by the application.

### 5. Prepare the ML model

The prediction service loads:

```text
backend/models/best_model.pkl
backend/models/feature_columns.pkl
```

If these files are already available and compatible with the environment, retraining is not required to start the service.

To train the models, ensure the cleaned dataset is available at:

```text
backend/models/processed_data/loan_approval_cleaned.csv
```

Then run this command from the `backend` directory:

```powershell
python models\train_model_v2.py
```

The training script compares the three classifiers and exports:

- Model comparison results.
- The selected model.
- The feature-column list.
- SHAP figures.

Confirm the dataset source and redistribution licence before uploading or sharing the CSV.

### 6. Start the backend

From the `backend` directory, with the virtual environment activated:

```powershell
python app.py
```

The local API runs at:

```text
http://127.0.0.1:5000
```

Check the Flask terminal output if your local configuration uses a different port.

### 7. Frontend setup

Open a second terminal.

From the project root:

```powershell
cd frontend
npm install
npm run dev
```

The frontend is normally available at:

```text
http://localhost:5173
```

The loan submission route permits this frontend origin. If Vite starts on a different port, keep the frontend URL and backend CORS configuration consistent.

### 8. Create users and use the app

The current frontend does not include a registration page. Create a user through the backend registration endpoint, then log in from the UI.

PowerShell example:

```powershell
$body = @{
    full_name = "Jane Doe"
    email = "jane@example.com"
    password = "ReplaceWithYourOwnTestPassword"
    role = "customer"
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:5000/api/v1/auth/register" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body
```

Use the same email and password on the login screen.

Officer accounts use the role `credit_officer`. Review role-assignment controls before exposing registration outside a local demonstration environment.

## Machine learning experiment

The recorded experiment used the cleaned input file:

```text
models/processed_data/loan_approval_cleaned.csv
```

### Experimental setup

| Item | Recorded value |
|------|----------------|
| Cleaned input table | 614 rows × 14 columns |
| Target | `loan_status` |
| Training records | 491 |
| Test records | 123 |
| Split | Single stratified 80/20 train–test split |
| Random seed | 42 |
| Test support: class 0 | 38 |
| Test support: class 1 | 85 |

The logged model input matrices contained 14 encoded features. The column count of the cleaned input table and the number of encoded model features describe different stages of preprocessing.

### Model configuration

| Model | Explicit settings |
|------|-------------------|
| Logistic Regression | `max_iter=5000`, `random_state=42`, `class_weight="balanced"` |
| Random Forest | `n_estimators=100`, `random_state=42`, `class_weight="balanced"` |
| XGBoost | `n_estimators=100`, `max_depth=4`, `learning_rate=0.1`, `random_state=42`, `eval_metric="logloss"` |

Feature scaling was used for Logistic Regression to address convergence.

### Test-set results

| Model | Accuracy | ROC-AUC | Precision: class 0 | Recall: class 0 | F1: class 0 |
|------|---------:|--------:|-------------------:|---------------:|------------:|
| Logistic Regression | 0.8374 | 0.8740 | 0.7250 | 0.7632 | 0.7436 |
| Random Forest | 0.8618 | 0.8523 | 0.7692 | 0.7895 | 0.7792 |
| XGBoost | 0.8455 | 0.8241 | 0.8065 | 0.6579 | 0.7246 |

| Model | Precision: class 1 | Recall: class 1 | F1: class 1 |
|------|-------------------:|---------------:|------------:|
| Logistic Regression | 0.8916 | 0.8706 | 0.8810 |
| Random Forest | 0.9048 | 0.8941 | 0.8994 |
| XGBoost | 0.8587 | 0.9294 | 0.8927 |

Random Forest achieved the highest accuracy and class-0 recall in this split and was selected for deployment. Logistic Regression achieved the highest ROC-AUC.

These results come from one train–test split. Cross-validation, confidence intervals, and an independent evaluation after model selection have not been reported.

Confirm the target encoding before interpreting class 0 as rejection and class 1 as approval. Approval labels should not be described as observed repayment or default outcomes.

## SHAP explanations

The training script exports three figures:

| File | Purpose |
|------|---------|
| `shap_beeswarm.png` | Distribution of feature contributions across explained test applications |
| `shap_importance.png` | Global feature importance based on SHAP contributions |
| `shap_waterfall.png` | Local explanation for test applicant index 0 |

The API returns the three features with the largest absolute SHAP values for the submitted application, together with their direction of influence.

The current online service uses:

```python
explainer = shap.TreeExplainer(model)
```

The offline figure-generation run used an explicit background dataset. Because these explanation configurations differ, their attributions should not be assumed identical.

SHAP explains how the model uses its inputs. It does not establish that a feature causes a lending outcome or that changing that feature will guarantee approval.

### 1. Log in

Send a customer login request to:

```text
POST http://127.0.0.1:5000/api/v1/auth/login
```

Copy the session token returned by the endpoint.

### 2. Submit an application

Create a new request:


Set:

```text

```

In **Body → raw → JSON**, provide:

```json
{
  "gender": "Male",
  "married": "Yes",
  "dependents": "1",
  "education": "Graduate",
  "self_employed": "No",
  "applicant_income": 50000,
  "coapplicant_income": 20000,
  "loan_amount": 200000,
  "loan_amount_term": 360,
  "credit_history": 1,
  "property_area": "Semiurban",
  "purpose": "Home Loan"
}
```

This is an integration-test example. Verify that income, loan amount, loan term, and derived features use the same units and transformations as the training data before interpreting the prediction.

### 3. Inspect the response

An observed local test returned HTTP `201 Created` with this response:

```json
{
  "application_id": 56,
  "credit_score": 100,
  "message": "Loan application submitted successfully",
  "ml_prediction": {
    "approval_probability": 0.41,
    "approved": false,
    "risk_score": 59.0,
    "top_reasons": [
      {
        "direction": "decreases approval chance",
        "feature": "coapplicantincome",
        "impact": -0.1005
      },
      {
        "direction": "decreases approval chance",
        "feature": "loan_amount_term",
        "impact": -0.0597
      },
      {
        "direction": "increases approval chance",
        "feature": "credit_history",
        "impact": 0.051
      }
    ]
  },
  "score_label": "Excellent",
  "status": "pending"
}
```

Actual application IDs, probabilities, scores, and contributions depend on the request, model artefact, and database state.

### Understanding the response

| Field | Meaning |
|------|---------|
| `credit_score` | Existing rule-based score |
| `score_label` | Label assigned to the rule-based score |
| `approval_probability` | API name for the selected model-class probability; verify the class mapping |
| `approved` | Model recommendation using the service threshold of 0.5 |
| `risk_score` | `100 × (1 − approval_probability)` |
| `top_reasons` | Three largest absolute SHAP contributions and their directions |
| `status` | Application processing status |

The `risk_score` is a transformation of the model output, not a validated probability of default.

A rule-based score and an ML recommendation can disagree. This is a reason to inspect the inputs, preprocessing, and explanations—not proof that either assessment is correct.

The displayed top three SHAP contributions are not expected to sum to the prediction without the baseline and all remaining contributions.

## Notes

- The backend expects PostgreSQL and uses the configuration in [backend/config.py](backend/config.py).
- The app uses stored session tokens for authentication rather than JWT.
- The officer workflow requires comments before a decision can be submitted.
- The ML recommendation does not replace the officer's recorded decision.
- ML results returned in the submission response are not necessarily persisted or available from other endpoints.
- Only load model files from trusted sources.
- Keep virtual environments, `node_modules`, credentials, session tokens, and database backups out of Git.

## Limitations and validation priorities

BankLite is an academic prototype, not a production-validated credit decision system.

Before using its ML output beyond demonstration:

- Verify the dataset source, licence, and target-label meaning.
- Match inference preprocessing to training, including feature names, encoding, missing-value handling, units, and derived-feature formulas.
- Avoid silently treating unexpected or missing features as zero.
- Verify probability-column selection against `model.classes_`.
- Evaluate repeated splits or cross-validation and use an independent final evaluation.
- Assess probability calibration.
- Evaluate fairness and the use of sensitive attributes or proxies.
- Test explanation stability across retraining and changing data.
- Validate authentication, role assignment, request validation, error handling, and secret management.

The current experiment does not separately evaluate first-time or thin-file borrowers, track repayment outcomes, or establish regulatory compliance.

## Conclusion

BankLite demonstrates a role-based loan origination workflow that combines customer application submission, rule-based scoring, officer review, audit logging, and AI-assisted review.

The ML extension adds Random Forest predictions and SHAP feature contributions to the loan submission response while preserving the existing pending-application and officer-decision workflow. Together, these components provide an academic platform for exploring explainable loan application decision support.
